# ADR 0004 — API عامة v1 فوق `generate-media` نفسها

**التاريخ:** 2026-10-22 · **الحالة:** معتمد (ينفّذ القرار 3 من ADR 0002)

## القرارات
1. **وظيفة واحدة اسمها `v1`** بلا JWT (`--no-verify-jwt`)، المصادقة بمفتاح API. المسارات على Supabase: `/functions/v1/v1/generate`، `/functions/v1/v1/assets/{id}`، `/functions/v1/v1/models`، `/functions/v1/v1/balance`؛ وبعد نقل DNS: `api.highlink.tech/v1/*` بإعادة كتابة واحدة على Cloudflare. المفتاح في `Authorization: Bearer hl_…` أو `X-API-Key`.
2. **النواة مشتركة**: منطق الخطوات التسع انتقل إلى `_shared/generate-core.ts` (`runGenerate`)، و`generate-media` (الواجهة بـJWT) و`v1` (مفتاح API) غلافان رقيقان عليه. مصدر حقيقة واحد للتسعير والأمان والحجز (المخطط §16).
3. **المفاتيح** (`api_keys`): `hl_live_` أو `hl_test_` + 32 حرفًا base64url من `gen_random_bytes(24)`؛ يُخزَّن `sha256` فقط + تلميح (آخر 4 أحرف)؛ يُعرض مرة واحدة عند الإصدار. الإصدار والإبطال عبر RPC بـ`auth.uid()` (`create_api_key`, `revoke_api_key`)؛ لا إدراج/تعديل مباشر من الواجهة. حد أقصى 10 مفاتيح نشطة لكل مستخدم.
4. **الحد اليومي** يُحسب على `POST /v1/generate` فقط (الطلبات المكلفة)، لكل مفتاح، بيوم UTC، ويُفحص ويُزاد ذريًا في `api_authenticate` (service_role). الافتراضي من الباقة: free 50، starter/basic 500، pro 2000، creators 5000؛ مفاتيح الاختبار 200. الرد يحمل `X-RateLimit-Limit/Remaining`، والتجاوز `429 DAILY_LIMIT`.
5. **`hl_test_` = تجربة جافة (sandbox)**: نفس التحقق والتسعير وفحص الأمان وفحص كفاية الرصيد، لكن بلا استدعاء مزوّد ولا حجز ولا خصم؛ الأصل يُسجَّل `completed` فورًا بـ`url=null` و`metadata.sandbox=true` و`metadata.would_cost`، ويُرسل webhook العميل كما في الحي. السبب: لا يوجد مزوّد sandbox، والهدف من مفتاح الاختبار اختبار التكامل (المصادقة، الحدود، idempotency، التوقيع) لا الصورة. يمكن تحويله لاحقًا إلى توليد حقيقي بسقف يومي بتغيير سطر واحد في `v1`.
6. **Idempotency-Key** على `POST /v1/generate`: صف `(key_id, idempotency_key)` يُحجز قبل التنفيذ ويحمل `sha256` للجسم المطبّع؛ نفس المفتاح ونفس الجسم → نفس الرد مع `Idempotency-Replayed: true`؛ نفس المفتاح وجسم مختلف → `409 IDEMPOTENCY_CONFLICT`؛ طلب متزامن قبل اكتمال الأول → `409`. بلا رأس → لا ضمان (كل طلب أصل جديد).
7. **webhook العميل** عند بلوغ الأصل حالة نهائية (من `provider-webhook`، ومن `v1` فورًا في sandbox): POST إلى `webhook_url` (من الطلب أو من المفتاح، https فقط) بمواصفة Standard Webhooks نفسها التي نتحقق بها من Replicate: `webhook-id`، `webhook-timestamp`، `webhook-signature: v1,<base64 HMAC-SHA256(id.ts.body)>` بسر `whsec_…` لكل مفتاح. الجسم `{ event: 'asset.completed'|'asset.failed', data: <asset> }`. 3 محاولات (0/2/6 ث) بمهلة 8 ث، تُسجَّل في `api_webhook_deliveries`، ولا تُفشل معالجة الـwebhook القادم من المزوّد أبدًا. إعادة الإرسال الدورية للفاشلة لاحقًا مع `cron-renewals`.
8. **تمثيل الأصل العام** (`toPublicAsset`) ثابت وموثّق: `id, status, type, model, prompt, aspect_ratio, resolution, url, thumbnail_url, cost_credits, sandbox, error{code,message}, created_at, completed_at`. لا يُسرَّب `metadata` الداخلي ولا معرّف مهمة المزوّد.
9. **الأخطاء**: `{ error: { code, message } }` بنفس رموز `GenerateErrorCode` + رموز API (`UNAUTHORIZED`, `NOT_FOUND`, `DAILY_LIMIT`, `IDEMPOTENCY_CONFLICT`, `INVALID_INPUT`) ورسائل عربية (القاعدة 10)؛ النسختان في `packages/shared` و`_shared` يحرسهما `contract.test.ts`.
10. **الترتيب**: API v1 قبل Kling (كما في ADR 0002 القرار 3)، لأن أول عميل لها هاي لينك نفسها (n8n) ولا تعتمد على الفيديو. `CLAUDE.md` محدّث.

## الأثر
- migration `0004_api_v1.sql`: `api_keys`, `api_daily_usage`, `api_idempotency`, `api_webhook_deliveries`, عمود `assets.api_key_id`، RLS لكلٍّ، ودوال `create_api_key / revoke_api_key / api_authenticate`. اختبارات `supabase/tests/api.test.sql` (تُكتب قبل الكود وتعمل على السحابة داخل معاملة تُلغى وفي CI).
- الواجهة: صفحة `/account` لإصدار وإبطال المفاتيح (المخطط §8 البند 8، الجزء الخاص بالتطبيقات المتصلة).
- `scripts/smoke-gate1.py`: حالة كاملة عبر API بمفتاح `hl_test_` (sandbox) وأخرى بمفتاح `hl_live_` (توليدة حقيقية + webhook العميل).
